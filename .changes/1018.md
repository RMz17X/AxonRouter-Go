# 1018 — Pinned-connection failures now penalize proxy pool fitness

## Symptom

- A stalling egress pool (ISP-BD-SG-06) hung two antigravity requests for
  the full 30s probe timeout on 2026-11-08 (~03:39–03:40 WIB) and stayed
  in rotation with a healthy-looking fitness score (71.9, no cooldown, no
  recorded failures). The operator had to bench it by hand.

## Root cause

- Pool fitness penalties (smart.FitnessTracker.RecordFailure /
  RecordFailureWithCooldown) were recorded only inside the
  multi-connection fallback loop in `handleAccountFallback` (and the
  combo loop). A request with a pinned connection — the idle prober pins
  every connection it checks (`PingConnection`), as does any client
  sending `x-connection-id` — takes the pinned shortcut straight to
  `tryForwardWithConnection` and never enters that loop, so its failures
  were never classified against the pool that served them. Successes on
  the same lane did reach the tracker (recorded inside
  `tryForwardWithConnection`), so a pool could look purely successful
  while hanging pinned attempts indefinitely.
- The two hung attempts were idle-probe pings (body "hi", model
  gemini-3.8-flash-low, ~29.9s each = the probe's 30s PingTimeout). The
  gateway log for the window shows fitness penalties for other providers'
  pools but none for the probe's pool, confirming the bypass.

## Fix

- New `internal/handlers/chat/pool_fitness.go`: `classifyPoolFailure`
  holds the loop's existing classification verbatim (location refusal →
  24h lock via RecordFailureWithCooldown + poolstate.MarkUnfit; transport
  failure → RecordFailure with progressive cooldown), resolving the
  serving pool via the shared `attemptPoolID` (ResolvedProxyPoolID, then
  the connection's configured pool; "__none__"/"direct" excluded).
- The fallback loop now calls `classifyPoolFailure` and keeps its
  exclude-and-retry behaviour on the returned pool.
- The pinned branch of `handleAccountFallback` classifies a failed
  attempt through the same helper before returning the error. No retry
  is added — pinned means pinned — but the pool verdict is now recorded,
  so two consecutive stalls on any lane bench the pool automatically
  (30s cooldown, then 2m + unfit mark at the second consecutive failure).
- ISP-BD-SG-06 itself was benched manually on staging (isActive=false)
  ahead of this fix; the fix is what makes the next stalling pool bench
  itself.
