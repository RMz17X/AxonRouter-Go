# 1033 — Provider stats: remove the SQL aggregate shortcut that bypassed the census

## Symptom (found in v1.9.54 live verification)
- GET /api/providers/stats served `"states":{}` for every provider:
  the per-state census of fragment 1031 never reached the client,
  even though computeProviderSummaryStats filled it.

## Root cause
- HandleProviderStats preferred a "high-performance" SQL GROUP BY
  fast path that built providerSummaryStat literals from
  total/connected/disabled counts only. The full computation ran
  only when the SQL path errored or returned no rows — effectively
  never. The same shortcut had been silently zeroing the error and
  exhausted fields (and lastErrorAt) all along; the strip's legacy
  fast-path derivation masked it while full lists were loaded.

## Fix
- The SQL shortcut is deleted. The handler always computes from the
  connection rows via computeProviderSummaryStats, so every field —
  census included — comes from the one derivation. The cost is
  bounded by the handler's existing 10-minute cache and by the
  Repo's snapshot cache behind GetProviderConnections; the endpoint
  serves the dashboard only.

## Verification
- go build + go vet on the dashboard package.
- Live on staging after deploy: the stats payload carries a states
  census per provider whose counts sum to total, and antigravity's
  census equals an independent per-row derivation over its
  connections (the client's own rules).
