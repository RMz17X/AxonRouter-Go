Request details now live in files, not in PostgreSQL. Every request attempt used to write its full diagnostic record — request and response payloads, ~10 KB a row — into the shared database as a blocking, never-droppable ledger insert, and every dashboard read (details page, analytics, failure leaderboards, node health, retention, provider renames) grouped that table on the spot. The records are diagnostics, not billing truth, so they moved to a file-backed store under the data directory: appends ride a bounded fire-and-forget queue onto append-only JSONL files (a full queue drops the record and counts it rather than ever parking a response), reads run over an in-memory index of per-record projections, and the one full-payload read fetches from a file offset. Retention keeps the old shape — a ~5,000-record ceiling plus the settings-driven age window — executed as file rewrites by the store's own retention pass and prune endpoint; a provider-node rename now rewrites the store's files alongside the ledger. The usage ledger (usageHistory) is untouched and stays in PostgreSQL. On first boot the store seeds itself from the legacy table, so the upgrade does not blank the Request Details page; the legacy table is left in place, simply no longer written or read.
