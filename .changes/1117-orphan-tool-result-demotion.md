MiniMax rejected a steady class of fleet requests with `400 invalid params, tool result's tool id(call_tool_2) not found (2013)` (120 failed attempts in 3 hours, retry storms across 14 connections). Root cause: the tool-call repair (PR #4090) stamped a fabricated `call_tool_<message index>` id onto orphan tool results — results whose conversation declares no matching assistant tool_call — curing the missing-id rejection by manufacturing a dangling-id one. Pairing-strict upstreams (MiniMax) reject the dangling id; lenient lanes had masked the defect. The repair now guarantees the real invariant — every tool result pairs with a call declared in the same body: id-less declared calls still receive synthetic ids (they pair, the call side carries the same id), an id-less result still adopts the next unpaired declared id, and an orphan result (no declared call left, or an id nothing declares) is demoted to a user message with its content preserved instead of receiving an invented id. The same fabrication in the translator's `EnsureToolCallIDs` is fixed the same way. Proven with the frozen real body before the fix: as-sent it reproduced the exact 2013 error against the MiniMax lane; with only the orphan demoted it was accepted and answered. One latent twin is recorded, not changed: the Responses-API transform (`internal/proxy/executor/transform.go`) still stamps `call_tool_<i>` for orphan `function_call_output` items — a different upstream family, unproven there, left for its own probe.
