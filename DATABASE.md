# PostgreSQL Database — Schema and Operator Contract

This document describes the storage contract implemented by the current
9router-go. **PostgreSQL is the only database.** The gateway boots on
`DATABASE_URL` alone; there is no embedded or file database in the build,
and a boot without `DATABASE_URL` is a fatal error that names the variable.

The schema sources are `internal/db/schema_pg.go` (bootstrap) and
`internal/db/schema_pg_defs.go` (declarative definitions). This document
summarizes them; the code is authoritative.

---

## 1. Bootstrap model — no migration runner

There are no migration files and no versioned migration runner. On every
boot, `EnsureCoreSchema` brings the connected database to the current
shape, additively and idempotently:

- missing tables are created (`CREATE TABLE IF NOT EXISTS`);
- missing columns are backfilled (the catalog is read **once** per boot
  and diffed in memory — one read, never a probe per column);
- the current and next month's partitions are ensured (§3);
- minimal seed rows are inserted with `ON CONFLICT DO NOTHING`
  (`_meta.schemaVersion = '1'`, the singleton `settings` row, the
  default plan).

Existing data is never dropped or retyped by the bootstrap. Because the
bootstrap is the schema mechanism, **upgrading the gateway is: deploy the
new binary against the same database.** The one structural exception is
the legacy import in §7, which is a separate one-shot tool.

Identifier rule that everything else follows: identifiers are written
unquoted everywhere, so PostgreSQL folds them to lowercase
(`providerConnections` is stored as `providerconnections`). When you
query by hand in `psql`, use the folded names or double-quote the
camelCase spelling.

### Type vocabulary

| Legacy/upstream type | PostgreSQL |
| --- | --- |
| `TEXT` | `text` (unchanged) |
| JSON document columns | `jsonb` — the columns SQL itself extracts from (`requestDetails.data`, `usageHistory.tokens`) plus whole-document payloads written only via `json.Marshal` (`settings.data`, `providerConnections.data`, `providerNodes.data`, `proxyPools.data`, `combos.models`, `usageDaily.data`, `usageHistory.meta`) |
| Integer counters (tokens, bytes, counts, epoch seconds, row-id refs) | `bigint` |
| Small flags, priorities, limits | `integer` |
| `REAL` | `double precision` |
| `BLOB` | `bytea` |
| `AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` |

Columns whose write contract admits non-JSON text (`kv.value`,
`apiKeys.metadata`, `combos.matchRules`, guardrail config) deliberately
stay `text`: a `jsonb` column would reject values those contracts allow.

## 3. Partitioning — the two hot ledgers

`usageHistory` and `requestDetails` are monthly `RANGE`-partitioned
tables, the shape AxonRouter's `schema.pg.js` established for the same
ledgers:

- **Partition key:** the `timestamp` column, kept `TEXT`. Every writer
  stamps zero-padded RFC3339 in UTC, for which lexicographic order *is*
  chronological order, so a month bound of `YYYY-MM-01` is a strict
  prefix bound and the plain range predicates the readers already use
  (`timestamp >= … AND timestamp < …`) get partition pruning.
- **Naming:** `<parent>_yYYYYmMM` (folded: e.g. `usagehistory_y2026m11`).
- **Ensured window:** the bootstrap creates the current and next month's
  partitions on every boot, so a write at a month boundary never lands
  before its partition does.
- **No DEFAULT partition, deliberately:** a row stamped outside the
  ensured window is a bug to surface, not traffic to file silently.
- **Primary keys** include the partition key — `(id, timestamp)` — as
  PostgreSQL requires for partitioned tables.
- **Indexes** are declared on the parent and maintained by PostgreSQL on
  every current and future partition. The usage parent carries the
  analytics covering indexes (`idx_uh_analytics`, the per-key/per-client
  token indexes `idx_uh_apikey_tok` / `idx_uh_clientkey_tok`, …) the
  dashboard reads depend on.

The migrator (§7) creates partitions for every month present in the
legacy source, not just the ensured window.

## 4. Connections and pool

The gateway connects with pgx through `DATABASE_URL`. The per-node pool
defaults to **maxOpen 10 / maxIdle 5**, overridable with
`PG_POOL_MAX_OPEN` / `PG_POOL_MAX_IDLE`. The sizing is deliberate for the
deployment target (small hardware): a 4-node cluster at 10 connections
per node holds 40% of PostgreSQL's default `max_connections=100`,
leaving headroom for the migrator and admin sessions, instead of one
node being able to pin a quarter of the server alone.

Both compose stacks pass the pool knobs through to the app service and
set PostgreSQL's side explicitly (`PG_MAX_CONNECTIONS`, default 100).
The invariant an operator must keep when resizing either side:

```
APP_REPLICAS × PG_POOL_MAX_OPEN + 10 (migrator/operator headroom) ≤ PG_MAX_CONNECTIONS
```

Raising the pool alone past the server's limit makes PostgreSQL refuse
connections (SQLSTATE 53300) and the gateway fail closed.

## 5. Retention

Retention is settings-driven, not hardcoded:

- `usageHistoryRetentionDays` bounds the usage ledger; the request-detail
  retention (`retentionDays`, plus `maxRequestRecords`) bounds
  `requestDetails`.
- A background retention loop prunes by age; the same prunes are exposed
  as dashboard maintenance actions (`POST /api/settings/database/prune`,
  `.../prune-usage` — always-protected routes).
- Pruning is **not** deletion of history's totals: the ledger carryover
  tables (§2) preserve the pruned aggregates, so long-range totals stay
  correct after the rows are gone.
- Operators who want instant space reclaim on a whole month can drop
  that month's partition (`DROP TABLE usagehistory_yYYYYmMM`) — the
  bootstrap only ever ensures the current and next month, and a dropped
  old partition is not recreated. Do this only for months the retention
  settings have already pruned or that you accept losing wholesale.

`VacuumDatabase` in the Go layer is a documented no-op on PostgreSQL —
space management is the server's autovacuum's job, not the gateway's.

## 6. The speed layer and the degradation model

PostgreSQL is the **single source of truth**. Above it sits the speed
layer (`internal/speedlayer`) for hot, ephemeral state only: usage
tracker live state (in-flight counters, name entries, the recent-request
ring), the proxy-pool rotation cursor, and the model-lock hot path.
Everything in it is reconstructible from PostgreSQL; nothing durable is
ever written only to the speed layer.

Backends, selected at boot:

| Configuration | Serving backend |
| --- | --- |
| `VALKEY_URL` / `REDIS_URL` set and reachable | Valkey/Redis (shared across nodes = cluster mode) |
| Redis configured but failing | **PostgreSQL** (the `speed_kv` / `speed_counters` tables in this same database) |
| No Redis configured | Per-node memory (single-node mode) |

The degradation rule is the load-bearing one: a Redis outage moves
serving to PostgreSQL behind a breaker (3 failures inside a 10 s
sliding window trip it, a 5-second prober heals it, both transitions are
logged and visible as `speedLayer` in `GET /api/system/memory`). It
**never** degrades to per-node memory in a cluster — divergent memory is
worse than a slower database. An unparseable Redis URL logs loudly and
serves from the database; it never silently selects memory.

The same payload carries `usageWritesDropped`: the count of usage
writes lost since this process booted — ledger rows (`usageHistory` /
`requestDetails`) that could not land, plus generic-lane jobs
(compression-analytics records) shed at a full queue — so the number
can over-report ledger loss but never under-reports it. The writer
counts every loss path — queue-full drops on the droppable lane and
rows its per-row fallback could not land. Zero is the only healthy value;
nonzero means investigate, starting with the gateway log's `[usage]`
lines. The counter covers losses while the process runs; a shutdown
that cannot drain within its grace window logs the fact and the tail
is lost uncounted.

Account cooldowns, rotation stamps, and upstream leases are *not* in the
speed layer: they were already database-serialized and stay that way.

## 7. Legacy migration (SQLite era → PostgreSQL)

The one-shot migrator is a **separate module and image**
(`tools/migrate-db`); it is the only shipped component that reads the
legacy file format as a source, and it is never linked into the gateway.

- Driven by the compose `migrate` profile — see the upgrade section of
  [`README.md`](README.md) for the operator steps.
- Copies every table in dependency order with ids, timestamps, and JSON
  payloads preserved exactly; bulk tables go through `CopyFrom`.
- **Refuses a non-empty target** unless `--truncate` is passed.
- Malformed rows are skipped **and reported** (table, row identity,
  column, reason); the closing verification requires
  `target = source − skipped` per table and fails loudly otherwise.
- Creates monthly partitions for every month present in the source.

The gateway also contains one other reader of that file format:
`internal/foreigndb`, a read-only reader for **other applications'**
files (browser cookie stores, Cursor/Zed state) behind the
import-from-browser features. It never opens this gateway's own data —
the gateway has no file to open.

## 8. Backup and restore

There is no application-level file backup anymore, because there is no
application file. **The restore point is the database server's own
backup** — this is also what the credential-vault migration pass states
in its log before sealing (its pre-migration snapshot used to be a file;
on a server database that restore point is `pg_dump`).

Against the compose stacks:

```bash
# Backup (single stack shown; the cluster stack is identical in shape)
docker compose -f docker-compose.single.yml exec postgres \
  pg_dump -U 9router -d 9router -Fc -f /tmp/9router.dump
docker compose -f docker-compose.single.yml cp postgres:/tmp/9router.dump ./9router.dump

# Restore into a FRESH, empty database (stop the app first so the
# bootstrap and writers are not racing the restore)
docker compose -f docker-compose.single.yml stop app
docker compose -f docker-compose.single.yml cp ./9router.dump postgres:/tmp/9router.dump
docker compose -f docker-compose.single.yml exec postgres \
  pg_restore -U 9router -d 9router --clean --if-exists /tmp/9router.dump
docker compose -f docker-compose.single.yml up -d
```

(The `-U`/`-d` values are the `POSTGRES_USER` / `POSTGRES_DB` from your
`.env`.) For an external PostgreSQL, run the same `pg_dump`/`pg_restore`
against it directly. After a restore, the next gateway boot re-runs the
additive bootstrap, so a dump taken from an older schema is brought
forward in place — take the backup *before* upgrading if you want a
rollback point, because the bootstrap only ever moves forward.

Don't forget the other half of an install: the `appdata` volume
(`DATA_DIR`) holds non-database state (CLI tokens/machine-id, uploads,
provider instruction files, tunnel state, catalog cache). Back it up
with any volume/file backup tool; it contains no database and needs no
special quiescing beyond stopping the app for consistency.
